# MP3 Recording Metadata Reference

This document describes the production MP3 files generated by this SDRTrunk build for downstream ingest, duplicate
matching, and call ordering logic.

## Scope

This reference applies to recorded MP3 call audio generated by SDRTrunk's audio segment recorder. It focuses on the
filename timestamp and ID3 metadata fields that identify call timing.

The canonical production call timestamp is `call_start_ms`. P25 system time fields are informational only and must not
replace `call_start_ms` for client-side call ordering, filenames, or ID3 creation date.

## Filename Format

Recorded MP3 filenames begin with a receiver-local formatted timestamp:

```text
yyyyMMdd_HHmmss_<metadata>.mp3
```

Example:

```text
20260612_165036_GCRCN-(Greater-Cleveland-Radio-Communications-Network)_GCRCNSimul_T-GCRCN__TO_56718_FROM_18006.mp3
```

The filename timestamp is derived from `call_start_ms`, truncated to whole seconds by the filename format. The filename
does not include milliseconds.

The filename timestamp is formatted using the receiver JVM's local timezone. Consumers should not parse the filename as
the primary timestamp when `call_start_ms` is available.

## ID3 Tag Summary

MP3 files include an ID3v2.4 tag. SDRTrunk writes standard audio tags and a semicolon-delimited comment string.

Important standard tags:

| Tag | Meaning |
| --- | --- |
| `title` | Target/talkgroup display text and aliases, when available. |
| `artist` | Source/radio display text and aliases, when available. |
| `album` | Channel name, when available. |
| `grouping` | System label, when available. |
| `genre` | `Scanner Audio`. |
| `date` / recording time | Human-readable call start date/time formatted as `yyyy-MM-dd HH:mm:ss.SSS`. |
| `year` | Receiver-local year derived from `call_start_ms`. |
| `comment` | Semicolon-delimited `key:value` metadata described below. |

## Comment Field Format

The ID3 comment is a single string of semicolon-delimited fields:

```text
key:value;key:value;key:value;
```

Example:

```text
Date:2026-06-12 16:50:36.515;System:GCRCN (Greater Cleveland Radio Communications Network);Site:GCRCNSimul;Name:T-GCRCN;Decoder:P25 Phase 1;Channel:LCN 00-1234;Frequency:853750000;call_start_ms:1781297436515;call_start_source:receiver_p25_control_grant;p25_system_time_estimate_ms:1781297434363;p25_system_time_quality:practical;
```

Parsers should split on `;`, ignore empty parts, and split each non-empty part on the first `:` only.

## Timing Fields

### `call_start_ms`

Type: integer string

Meaning: Receiver-local UTC epoch milliseconds for the production call start.

This is the main timestamp for ingest. Use this for:

- database call time
- canonical call ordering
- duplicate matching windows
- public timeline placement
- ID3 creation-date equivalent logic

This field is not derived from P25 system time. It is the receiver computer's local clock at the selected call-start
event.

### `call_start_source`

Type: string enum

Allowed values:

| Value | Meaning |
| --- | --- |
| `receiver_p25_control_grant` | `call_start_ms` came from the receiver-local timestamp on the P25 control-channel traffic grant. |
| `receiver_first_audio_buffer` | Fallback. `call_start_ms` came from the receiver-local timestamp when the first decoded audio buffer was added. |

`receiver_p25_control_grant` is preferred because it is earlier in the call path and is less affected by voice-channel
setup, decoding, buffering, and recorder-write delay.

`receiver_first_audio_buffer` means no grant timestamp reached the audio recording path. The timestamp is still valid
for production use, but it may be later than the actual channel grant.

### `p25_system_time_estimate_ms`

Type: integer string or literal `null`

Meaning: Optional interpolated estimate of the P25 system clock at `call_start_ms`.

This field is informational. It may be useful for server-side cross-receiver reconciliation, but it must not replace
`call_start_ms` as the official client-side timestamp.

When present, it is calculated as:

```text
latest_p25_system_time_ms + (call_start_ms - latest_p25_system_time_observed_receiver_ms)
```

If no usable estimate is available, the value is the literal string:

```text
null
```

### `p25_system_time_quality`

Type: string enum

Allowed values:

| Value | Meaning |
| --- | --- |
| `locked` | P25 system time was sane, microslots were locked, and the broadcast said the system clock was locked to an external reference. |
| `practical` | P25 system time was sane and microslots were locked, but the broadcast did not report external-reference lock. Useful as a matching hint, not as truth. |
| `unusable` | A P25 sync message was seen, but the time was clearly bad or not safe to use for estimates. |
| `unavailable` | No P25 sync sample was available for this call, or the call used first-audio-buffer fallback timing. |

Consumers should only compare `p25_system_time_estimate_ms` when quality is `locked` or `practical`.

## Timezone Rules

`call_start_ms` and `p25_system_time_estimate_ms` are UTC epoch milliseconds. They are timezone-independent.

The filename prefix and the comment `Date` field are formatted using the receiver JVM's local timezone.

Recommended ingest order:

1. Use `call_start_ms` if present and positive.
2. Otherwise parse the comment `Date` using the receiver/node timezone when known.
3. Otherwise parse the filename prefix using the receiver/node timezone when known.
4. Otherwise use server receive time as a last resort.

## Duplicate Reconciliation Guidance

Use `call_start_ms` as the primary timing input for duplicate matching. Do not use `p25_system_time_estimate_ms` as the
canonical call time.

Suggested initial duplicate candidate query:

```text
same system label
same target/talkgroup
call_start_ms within +/- 1500 ms
different receiver node preferred
duration roughly similar, for example +/- 2 to 4 seconds
source/radio same if present, but do not require it
```

Do not require the same frequency. The same talkgroup audio may be carried by different sites or channels.

If both calls have `p25_system_time_quality` of `locked` or `practical`, compare `p25_system_time_estimate_ms` as an
additional confidence signal. A close P25 estimate should strengthen a duplicate match; a missing, unavailable, or
unusable estimate should not prevent a match.

Recommended handling:

- Insert one public/canonical call row for the event.
- Store other receiver recordings as variants or alternates tied to the canonical call.
- Prefer an operator-configured receiver-node priority when choosing the canonical audio copy.
- Otherwise keep the first accepted call as canonical.

## Backward Compatibility

Older recordings may not contain the four production timing fields:

```text
call_start_ms
call_start_source
p25_system_time_estimate_ms
p25_system_time_quality
```

In that case, ingest should fall back to the historical `Date` comment and then to the filename prefix.

The new fields are appended to the existing comment string and do not change the existing `Date`, `System`, `Site`,
`Name`, `Decoder`, `Channel`, or `Frequency` fields.

## Field Use Summary

| Field | Use for canonical time? | Use for duplicate matching? | Notes |
| --- | --- | --- | --- |
| `call_start_ms` | Yes | Yes | Primary production timestamp. |
| `call_start_source` | No | Yes | Helps choose confidence/window size. |
| `p25_system_time_estimate_ms` | No | Optional | Compare only when quality is `locked` or `practical`. |
| `p25_system_time_quality` | No | Yes | Determines whether the P25 estimate should be considered. |
| Comment `Date` | Fallback only | Fallback only | Local formatted date string. |
| Filename prefix | Fallback only | Fallback only | Local formatted, whole-second precision only. |
